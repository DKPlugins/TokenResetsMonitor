# Upgrading and rolling back

Install exact versions. Read the release notes before updating, including schema changes and the minimum Go version if you build from source. The process checks release metadata when enabled but never downloads or installs executable updates.

Application SemVer and the three schema versions are separate. A compatible application update preserves the meaning of existing configuration and delivery IDs. For 1.2, configuration and state schemas are `3`; webhook `schema_version` remains `1`. Version 1 and 2 configuration files remain readable and are normalized in memory.

## Check before installing

```sh
tokenresetsmonitor check-update --json
tokenresetsmonitor doctor --config ./config.yaml
tokenresetsmonitor doctor --offline --config ./config.yaml
```

`check-update` reads GitHub Releases over HTTPS with time/body limits and conditional requests. Stable releases are selected by default; `updates.include_prerelease: true` includes candidates from the most recent 100 release records. It compares SemVer correctly, including numeric prerelease components, and returns the release page, availability, and declared compatibility. An available release still returns exit 0; a network/protocol error returns 1 and a diagnostic message.

Background checks run every 24 hours unless `updates.enabled: false`. Rate limits defer retries. No GitHub token is required for public release metadata. Missing/malformed metadata or a failed check does not mean the installation is current.

New releases publish `compatibility.json` containing `manifest_version`, application version, supported configuration/state schema ranges, webhook/API schemas, and native platforms. The declared result is `supported`, `incompatible`, or `unknown`; older releases without a manifest are unknown. This compares the release to the running binary's contracts. It is not proof that a particular filesystem, custom template, or service environment works.

Doctor checks configuration and platform, reads a current running status snapshot for state compatibility, and makes read-only source catalog/provider/event requests to validate API schema and complete pagination. Its total API deadline is 30 seconds. It never opens/migrates the live database or sends notifications. Offline mode makes no network requests. Missing/stale daemon metadata is unverified rather than guessed. Directory inspection checks existence/accessibility, not effective write permission under another service account.

## Before an update

1. Run `version` and `status --config ...`; record the current version and pending/failed counts.
2. Stop the process, Windows service, systemd service, or container and ensure no other process uses the database.
3. Back up the configuration, state database and its sibling status snapshot, and current executable or image tag. Keep backups private: database records can contain announcement details and destinations.
4. Verify the new archive against the release's `checksums.txt` and validate configuration with the new binary.
5. Install the new version, start it, then check status and logs. Source API failures may leave a provider temporarily unready without indicating an installation failure.

Do not copy a live bbolt database as an ordinary file backup. Stop the writer first. Migration backups generated by the program use a consistent bbolt read transaction.

## Installer-managed updates

Run the installer again with a new `--version` (Linux) or `-Version` (Windows). Existing configuration and state are preserved. The installer stops the existing service, saves the old binary/configuration/data, replaces the binary, validates configuration, and starts the service unless `--no-start`/`-NoStart` was supplied.

Linux backups are under `/var/backups/tokenresetsmonitor/<UTC-timestamp>-<id>/`. Windows backups are under the installation's data directory in `backups\<UTC-timestamp>-<id>\`. The default state directories are backed up automatically; **if you changed `state_path` outside those directories, back that path up yourself before invoking the installer**. Existing application log settings are not rewritten.

An installer failure leaves its backup in place and prints its location. Check whether the service is stopped before attempting restoration. The installer does not silently restart an older executable against a potentially migrated database.

## Docker updates

```sh
docker compose stop monitor
# Back up the stopped monitor-data volume using your normal volume backup tool.
# Set TRM_VERSION to the desired exact published tag in .env or your shell.
docker compose pull monitor
docker compose up -d monitor
docker compose logs --tail 100 monitor
docker compose exec monitor tokenresetsmonitor status --config /config/config.yaml
```

Keep the volume name unchanged. `docker compose down --volumes` deletes monitoring history and pending deliveries and is not an update command. Retain the previous image tag/digest and a matching stopped-volume backup for rollback.

## Schema migration

Database migrations are sequential transactions. Before an existing older schema is changed, the application creates a sibling file named `state.db.backup-<timestamp>` (using your actual database name). If backup or migration fails, startup fails. A future schema that this binary does not understand is refused rather than modified.

Configuration migration is explicit and does not expand `${NAME}` secret references into persisted values:

```sh
tokenresetsmonitor config migrate --config ./config.yaml
tokenresetsmonitor config migrate --apply --config ./config.yaml
tokenresetsmonitor config validate --config ./config.yaml
```

The first command previews the transition; `--apply` writes it and retains the original in a sibling `config.yaml.backup-<timestamp>`. Files already at the current version are left unchanged. Version 1 and 2 files remain readable by 1.2 without rewriting. New 1.2 settings require the 1.2 binary; earlier validators reject schema 3 and its new fields. Keep the original configuration for rollback. Unknown future configuration versions are refused.

## Moving from 1.0 or a 1.1 candidate to 1.2

The first 1.2 daemon startup migrates supported state to schema 3 and retains a sibling pre-migration backup. Existing notification IDs, acknowledgements, pending work, and destination cooldowns are preserved. Upgrading does not replay baseline announcements. Earlier releases did not retain individual attempt histories or all historical filter decisions, so migrated records identify unavailable detail.

A 1.0 or 1.1 binary cannot read schema 3. Keep the pre-migration database and matching old configuration for rollback; merely replacing the executable is insufficient. A rollback to an older backup may resend deliveries acknowledged after that backup, which is why receivers should deduplicate notification IDs.

Correction and withdrawal messages are enabled by default for Telegram and Slack; use `notify_changes: false` in a channel to disable them. Webhooks retain their existing ordinary-announcement behavior unless `webhook.notify_changes: true` is explicitly set. Adapt custom receivers/templates to distinguish change notifications before enabling it. These messages refer to announcements previously acknowledged by the same destination; merely enabling a channel does not subscribe it to old history.

Detailed history is retained indefinitely by default (`history.retention_days: 0`). A positive retention period removes expired detail while keeping the durable identity and suppression markers needed to avoid replay. See [history and delivery management](history.md).

## Rollback

Stop the current process. Preserve its database separately before restoring anything. Restore the old executable/image plus a configuration and state backup known to be compatible with that version. If the current state schema is still supported by the old executable, its existing database may be retained; verify this against the release notes rather than assuming it.

Restore the entire state directory from a stopped backup, keeping the original ownership and access permissions. On Windows, use native PowerShell file operations and retain LocalService access to data/logs. On Linux, state/log directories must remain writable by the `tokenresetsmonitor` user. Start the old version and inspect status/logs before resuming routine operation.

Restoring older state also restores its knowledge of acknowledgments. Notifications delivered after that backup may be attempted again. Webhook receivers should deduplicate persistent `Idempotency-Key` values; Telegram duplicates may need to be recognized by event and time. Rollback can also omit work created after the backup, so preserve the failed-update data until reconciliation is complete.

A target release must publish the exact archive for the current OS/architecture; a platform declaration alone is insufficient. If its schema ranges drop a legacy format still accepted by this binary, compatibility remains unknown until the installation is inspected/migrated. The checker reads release metadata and compatibility.json only; it never downloads the executable archives.
